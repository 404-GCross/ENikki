## 项目简介

ENikki 是一款面向 ACG 圣地巡礼用户的跨平台行程规划工具。它希望把散落在作品资料、巡礼点位、地图、截图、笔记和预订页面中的信息，整理成一份**真正可以执行、可以随时调整、可以在现场使用**的巡礼行程。

ENikki 不只是一个点位收藏器，也不只是一个地图应用。它的核心目标是完成从“想去看看”到“顺利走完”的完整闭环：

- 从作品出发，发现并整理巡礼点位；
- 把点位编排成符合时间、距离和游览顺序的路线；
- 规划城际交通、市内交通、住宿区域、每日用餐与整趟行程预算；
- 将交通、住宿和餐厅预约导向可信的第三方平台；
- 在巡礼途中提供离线资料、导航跳转和打卡记录；
- 在行程结束后沉淀照片、足迹、花费和可分享的旅行记录。

## 为什么需要 ENikki

一次完整的圣地巡礼，通常要在多个工具之间来回切换：

| 常见问题 | ENikki 希望提供的解决方式 |
| --- | --- |
| 作品、点位和截图分散在网站、地图与收藏夹中 | 以作品和行程为中心统一管理点位、参考图与来源 |
| 地图上的点很多，但不知道怎么安排顺序 | 按城市、片区、开放时间和交通方式辅助排线 |
| 路线看起来合理，实际却赶不上车或走不完 | 估算移动时间、停留时间与每日强度，提示冲突 |
| 交通、住宿、用餐和花费要另行手工计算 | 在同一行程中安排交通、住宿和餐次，并统一计算分类预算 |
| 现场网络不稳定，需要反复切换应用 | 出发前缓存行程，现场提供离线查看、打卡与导航跳转 |
| 回来后照片、地点和花费难以对应 | 按行程和点位汇总记录，导出可追溯的旅行档案 |

## 核心功能

> 以下均为目标功能。具体交互、数据来源与交付顺序会在设计和验证过程中调整。

### 1. 作品与巡礼点发现

- 按作品名称、别名和作品类型搜索巡礼作品。
- 在 ENikki 内直接打开巡礼地图，浏览和筛选取景地，并单选、多选或按当前视野批量加入行程；不依赖嵌入 Anitabi 网页。
- 查看点位的坐标、场景截图、出现话数、地点说明、来源和补充信息。
- 查看附近巡礼点，并把候选点位加入收藏或指定行程。
- 支持从 Bangumi 导入作品、从 Anitabi 按需导入点位，以及手动添加；导入时保留来源与更新时间。
- 记录“想去”“已加入路线”“已打卡”等状态，避免重复整理。

第一阶段只使用 Bangumi 搜索作品和获取作品资料，并以其 `subjectID` 按需关联
Anitabi 巡礼点位。Bangumi 查不到的作品可以手动创建，但暂不自动支持 Anitabi
点位导入。

Bangumi 接入、缓存、限流和 Anitabi 关联流程见
[`docs/BANGUMI_INTEGRATION.md`](docs/BANGUMI_INTEGRATION.md)。

### 2. 行程与路线规划

- 创建单人或多人的巡礼行程，设置日期、出发地、目的地、交通偏好和预算上限。
- 支持“按作品规划”和“按城市规划”两种入口。
- 将点位按城市、片区和景点聚类，再拆分为每日路线。
- 在计划总览时间线中直接添加、编辑、删除、拖动和锁定巡礼点、交通、住宿、用餐、拍照打卡及备注。
- 调整游览顺序、停留时长、出发时间和交通方式，并在地图上同步预览。
- 估算步行、公共交通、驾车等方案的距离、时间和费用。
- 根据营业时间、预约要求、首末班车和日照时间给出可行性提示。
- 将路线发送到系统地图或第三方地图应用完成实时导航。
- 支持行程复制、模板、版本回退和导入导出，方便为不同日期或同行者调整方案。

### 3. 交通与住宿

ENikki 会覆盖交通和住宿的**规划环节**，但不直接承担交易环节。

- 记录并比较多段城际交通方案，包括时间、预估费用、换乘和备选路线。
- 规划市内公共交通、步行、骑行、自驾和出租车等组合方式。
- 为住宿选择提供区域建议，例如到主要点位的通勤时间、交通便利度和预算区间。
- 将火车、航班、巴士、酒店等预订入口跳转到第三方平台，由用户自行核对库存、价格、退改和交易条款。
- 保存已选方案和预订信息摘要，以便离线查看；敏感订单信息默认不进入公开分享内容。

交通、住宿、用餐和预算的完整数据模型与 P1 验收标准见
[`docs/TRIP_PLANNING.md`](docs/TRIP_PLANNING.md)。

程序分层、数据库、排线器、预算计算和离线导入实现见
[`docs/TRIP_PLANNING_ARCHITECTURE.md`](docs/TRIP_PLANNING_ARCHITECTURE.md)。

### 4. 用餐安排

- 按天安排早餐、午餐、晚餐、咖啡、甜点、夜宵和临时用餐。
- 支持指定餐厅、按区域选餐和只保留时间窗的弹性安排。
- 记录餐厅地址、营业时间、预约要求、排队时间、菜单摘要和人均预算。
- 记录同行者的饮食偏好、过敏项、儿童餐和其他特殊需求。
- 将餐厅位置加入地图和每日时间线，检查用餐时间与巡礼路线是否冲突。
- 支持合作咖啡厅、主题餐厅和联动活动的预约信息记录。
- 餐厅座席预约和套餐购买只跳转第三方平台，ENikki 不直接下单或收款。
- 已确认的餐厅和预约信息可离线查看。

### 5. 预算管理

- 按交通、住宿、餐饮、门票、活动、购物和其他类别建立预算。
- 同时支持预估金额、实际金额、人均金额和团体总额。
- 支持同时设置基准币种和第二显示币种，例如 CNY + JPY。
- 保留每笔费用的原币种，总预算、分类和每日汇总同时显示两种金额。
- 支持汇率来源、生效时间、固定费用和按人数分摊。
- 在行程规划阶段提前显示预算占用比例，并提示超支风险。
- 在旅途中快速补记支出，在结束后生成分类汇总。

实时价格、汇率、班次、房态和库存均由第三方提供，可能存在延迟或变化；最终结果应以预订平台和运营方为准。

### 6. 拍照打卡与现场记录

- 拍照打卡是时间线中的安排类型，可通过右上角“添加”或已有事件的“编辑”进入。
- 默认显示“参考图 + 实拍图”两个空图片框，点击后选择 Anitabi、拍照、
  手机相册或本地文件。
- 支持参考图叠影、上下对比、左右对比、原图/实景切换。
- 支持继续添加多组对比图片。
- 保存拍摄时间、可选位置、现场备注、参考图和实景照片。
- 打卡完成后自动绑定作品、点位、行程和当前日期，并更新完成进度。
- 支持多张照片、重拍、删除、补充备注和标记“稍后补拍”。
- 对点位补充“已关闭”“无法进入”“拍摄受限”等状态，避免其他用户重复踩坑。
- 照片默认保存在本地，只有用户主动开启同步后才上传。
- 定位、相机和相册权限按需申请，并允许用户完全关闭相关能力。

### 7. 记录、分享与协作

- 以地图、时间线和作品维度回顾已经完成的巡礼。
- 生成包含路线、打卡点、照片和花费摘要的旅行报告。
- 导出结构化行程与记录，避免数据被锁定在单一客户端。
- 分享时可选择隐藏精确位置、订单信息、同行者姓名和其他敏感字段。
- 长期支持多人共同编辑、变更确认和离线合并；同步冲突应可见、可恢复。

### 8. 跨平台与数据同步

- 目标平台：Windows、Linux、macOS、Android、iOS 和 HarmonyOS。
- 采用本地优先设计：没有账号或网络时，仍可创建、编辑和查看核心行程。
- 账号与云同步为可选能力，不登录不应阻塞本地使用。
- 同一行程可以在桌面端和移动端协同使用；具体同步策略与冲突处理将在技术设计阶段确定。
- 不追求各平台像素级一致，但应保持核心概念、数据格式和交互逻辑一致。

## 产品边界

为避免“一站式”变成无边界的范围扩张，ENikki 明确以下边界：

- **预订只跳转**：ENikki 暂不直接售卖车票、机票、酒店、餐厅套餐或预约库存，不处理支付、退款、改签和售后。
- **不做价格承诺**：班次、价格、营业时间和开放状态可能变化，客户端展示值必须标注来源与更新时间。
- **不以抓取代替授权**：数据接入优先使用官方 API、开放许可或明确授权，不绕过平台限制。
- **不分发无授权内容**：动画截图、作品素材和第三方点位数据不会仅因可访问就被纳入仓库或随安装包分发。
- **首版不做内容社交平台**：评论、投稿审核、用户关注和内容运营会在核心行程闭环稳定后评估。
- **不替代现实判断**：路线结果只是决策辅助，用户仍需遵守当地法律、交通规则和场地要求。

## 典型使用流程

```mermaid
flowchart LR
    A[创建巡礼行程] --> B[选择作品与点位]
    B --> C[地图聚类与自动排线]
    C --> D[调整时间、交通与每日强度]
    D --> E[规划交通与住宿]
    E --> F[安排每日用餐]
    F --> G[核对预算并跳转预订]
    G --> H[缓存行程并出发]
    H --> I[导航、巡礼与打卡]
    I --> J[复盘、导出与分享]
```

一次典型使用过程如下：

1. 新建行程，填写日期、出发地、目的地和同行人数。
2. 搜索想巡礼的作品，把目标点位加入候选清单。
3. 在地图上检查分布，让 ENikki 给出初步的分区和每日路线。
4. 根据体力、兴趣和开放时间调整顺序、停留时长与交通方式。
5. 规划城际交通、市内交通和住宿区域，通过第三方链接完成实际预订。
6. 安排每天的餐次、餐厅或用餐区域，并记录预约和饮食限制。
7. 设置交通、住宿、餐饮、门票和其他分类预算，检查总花费。
8. 出发前缓存交通、住宿、餐次、路线、参考图和离线资料。
9. 巡礼途中按清单导航、用餐、打卡和补记，必要时重排后续安排。
10. 行程结束后汇总足迹、照片和花费，导出或分享旅行报告。

## 设计原则

### 行程优先，而不是信息堆积

所有作品、点位和内容最终都应服务于一份可执行的行程。单纯增加收藏、榜单或社区信息，不应以牺牲规划效率为代价。

### 数据可追溯

点位、图片、价格、班次和营业时间都应尽可能显示来源、许可和更新时间。无法确认的信息不伪装成事实。

### 本地优先，隐私默认

核心能力优先离线可用；定位、相册和账号同步均按最小必要原则启用。用户的精确位置、订单与私人照片默认不上传、不公开。

### 开放与可迁移

开源代码，公开关键数据格式，并提供导入导出能力。用户应能够离开 ENikki，而不是被数据格式锁定。

### 对社区与现实环境负责

巡礼不应打扰居民、学校、宗教场所和正常经营秩序。产品应呈现拍摄礼仪、禁入区域和现场规则提醒，避免把“打卡”变成侵入式行为。

## 数据、版权与合规

ENikki 的代码以 AGPL-3.0 开源，但**代码许可证不自动覆盖第三方作品、图片、地图、交通、价格或酒店数据**。

### 计划使用的数据类型

| 类型 | 可能的来源 | 原则 |
| --- | --- | --- |
| 作品资料 | Bangumi | 第一阶段唯一作品源，遵守 API 条款并保留原始链接 |
| 巡礼点位与参考图 | Anitabi 等社区数据源、用户自有数据 | 先确认授权；不在仓库中擅自分发原始数据 |
| 地图底图与地理编码 | OpenStreetMap、商业地图服务或自托管服务 | 保留版权署名，遵守调用频率与展示要求 |
| 交通、住宿与餐厅信息 | 官方或第三方查询接口、地图 POI、用户录入 | 标注更新时间；预订和预约跳转到外部平台 |
| 用户内容 | 用户主动录入或导入 | 用户保留权利；分享前取得明确授权 |

### 内容与隐私要求

- 动画截图、作品名称、角色形象和相关素材的权利归原权利方所有，仅用于必要的场景对照与信息说明。
- 用户贡献点位或照片时，应确保自己有权提交，并尊重被拍摄地点和其他人的隐私。
- 精确坐标、家庭住址、订单编号、证件信息等敏感数据不得默认公开。
- 项目需要建立内容举报、纠错和下架流程；收到有效权利通知后应及时处理。
- 使用地图、交通和住宿服务时必须遵守对应平台条款，不将第三方接口伪装成 ENikki 自有数据。

## 技术方向

技术栈、框架和部署方式尚未定稿。在进入开发前，项目会通过 ADR（Architecture Decision Record）记录关键决策，避免在没有验证的情况下过早绑定方案。

详细的技术选型、模块设计、数据模型、路线算法和分阶段交付方案见 [`docs/IMPLEMENTATION_PLAN.md`](docs/IMPLEMENTATION_PLAN.md)。

服务端的职责、部署、缓存和客户端降级策略见
[`docs/SERVER_ARCHITECTURE.md`](docs/SERVER_ARCHITECTURE.md)。

已经确定的技术原则包括：

- 跨平台客户端共享尽可能多的领域模型与业务逻辑，同时保留各平台必要的能力差异。
- 外部数据源通过适配层接入，避免作品、地图、交通或住宿供应商与核心业务强耦合。
- 地图服务抽象化，支持按地区、成本和授权要求切换供应商。
- 本地数据库和离线缓存是一等能力，而不是联网失败后的补丁。
- 服务端保持可选和尽量简单；若提供网络服务，其源码同样遵守 AGPL-3.0。
- 核心规划逻辑、数据迁移、预算计算和同步冲突处理必须具备自动化测试。
- 接口密钥、用户凭据和第三方数据不得提交到公开仓库。

代码仓库初始化后，本节会补充真实的开发环境、目录结构、启动命令、测试命令和发布流程。

## 路线图

路线图只表达依赖顺序，不代表已经承诺具体发布日期。

### P0：定义与验证

- 访谈不同经验层次的 ACG 巡礼用户，验证排线、交通、住宿、用餐和预算中的真实痛点。
- 梳理核心领域模型，包括作品、点位、行程、日程、交通段、住宿、餐次、预算和打卡记录。
- 评估可用数据源、授权边界、更新机制和离线缓存策略。
- 完成跨平台技术选型与最小技术验证。
- 明确隐私政策、内容政策和第三方服务清单。

### P1：可执行行程闭环

- 支持作品搜索、点位导入、手动添加和地图浏览。
- 支持创建行程、点位分组、每日排线，以及交通、住宿、用餐和预算规划。
- 支持交通、住宿和餐厅预约信息记录，并把预订或预约操作跳转到第三方平台。
- 支持行程导入导出、移动端离线查看和基础打卡。
- 至少在一个桌面平台和一个移动平台完成可验证原型。

### P2：完整巡礼体验

- 完善时间冲突、路线强度、营业时间、用餐预约和交通衔接提示。
- 支持多币种预算、实际支出、用餐记录、旅行记录和分享报告。
- 支持可选账号、跨设备同步和多端离线冲突恢复。
- 扩展平台覆盖，并补齐无障碍、国际化和本地化能力。
- 建立稳定的数据适配层、错误监控和版本迁移机制。

### P3：开放生态

- 发布公开数据格式、导入导出规范和稳定 API（如有需要）。
- 评估社区点位补充、纠错审核和多人协作能力。
- 与合规的数据提供方、地图服务和巡礼社区建立长期合作。
- 在不破坏隐私与版权边界的前提下，支持插件或第三方数据适配器。
