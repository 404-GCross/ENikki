# MiriaGo 项目流程与可借鉴点

> 调研日期：2026-09-14  
> 调研对象：[BilyHurington/MiriaGo](https://github.com/BilyHurington/MiriaGo)  
> 参考版本：v1.1.6，main 分支约 3dd5296  
> 项目许可：MIT  
> 说明：本文只做产品和工程设计分析，不复制 MiriaGo 代码；复制代码时必须保留其许可和版权声明。

## 1. 核心结论

MiriaGo 的价值不在于技术栈本身，而在于它验证了一条可行的产品路径：

```text
创建计划
→ 搜索作品
→ 在地图导入点位
→ 按片区整理
→ 手动排序
→ 离线缓存参考图
→ 现场导航和拍摄
→ 打卡记录
→ 导出数据包
```

它暂时没有做账号、云同步、复杂交通规划、预算或预订，也没有实现严格的
多日路线优化，但仍然形成了完整可用的巡礼闭环。

ENikki 应当重点借鉴：

- 本地优先，不依赖账号服务。
- “片区”作为排线前的最小组织单位。
- 点位状态、当前目标和完成进度。
- 地图内点位导入和选择。
- 缩略图与完整参考图分级缓存。
- 可预览、可选择内容的导入导出数据包。
- 作品、点位和记录的数据快照。
- 完善的用户指南、隐私说明、测试和发布流程。

不应直接照搬：

- 客户端硬编码 Bangumi 令牌。
- 依赖未公开的 Anitabi `g*.json` 静态接口。
- 将大量界面和持久化逻辑写进超大文件。
- 在没有验证的平台目标上复制其 Tauri 桌面结构。
- 在核心闭环稳定前优先开发自动调色和复杂拍摄功能。

## 2. 用户使用流程

### 2.1 创建计划

一个计划通常对应：

- 一天或一次出行；
- 一个城市；
- 一个作品专题；
- 一个自定义巡礼主题。

计划包含名称、地区、作品、点位、片区、当前目标和备忘。应用支持多个计划，
并记住当前激活的计划。

### 2.2 添加作品

作品有两种来源：

- Bangumi 搜索；
- 手动添加。

如果后续要导入 Anitabi 点位，优先使用 Bangumi，因为 Anitabi 使用
`subjectID` 关联作品。手动作品用于 Bangumi 查不到或用户不想关联的情况。

### 2.3 从 Anitabi 地图导入点位

流程：

1. 选择已经关联 Bangumi ID 的作品。
2. 在应用内加载 Anitabi 点位。
3. 地图显示点位和聚合标记。
4. 点击点位查看缩略图、名称、集数、时间和来源。
5. 将点位加入当前计划。
6. 缓存点位元数据和缩略图。
7. 之后可以单独缓存完整参考图。

这是 MiriaGo 最值得 ENikki 复现的主流程。

### 2.4 建立片区

片区是比“每日路线”更轻的安排方式，例如：

- 宇治站附近；
- 大吉山；
- 平等院表参道；
- 晚间灯光区域。

片区包含名称、顺序、排序模式、关键点、关键点坐标和备注。关键点通常是
车站、路口、桥或片区中心，用来帮助判断点位归属和现场定位。

这个模型非常适合 ENikki 第一阶段。它不需要一开始解决复杂的多日 VRP，
但已经能让用户按现实区域推进巡礼。

### 2.5 整理顺序

MiriaGo 的排序分两级：

- 片区之间的顺序；
- 片区内部点位的顺序。

片区内有两种模式：

- 无序：适合点位密集、现场自由移动。
- 手动排序：适合按街道、坡道或交通方向推进。

这和 ENikki 的目标一致，但实现成本远低于完整自动排线。ENikki 可以先支持
手动顺序和简单建议，再增加自动优化。

### 2.6 出发前离线准备

用户需要提前完成：

- 作品和点位整理；
- 片区与顺序确认；
- 参考图批量缓存；
- 数据包备份。

离线可用：本地计划、点位、记录、缩略图和已缓存完整参考图。

离线不可用：未缓存地图、新 Anitabi 点位、Bangumi 搜索和远程图片。

这里的重要经验是：离线不是“整个应用离线”，而是明确列出哪些内容必须提前
缓存，并让用户在出发前完成检查。

### 2.7 现场使用

地图页面负责显示当前位置和计划点位，实时导航跳转外部地图应用。点位详情
可以打开拍摄参考：

- 参考图叠影拍摄；
- 上下对照拍摄；
- 从相册导入照片；
- 保存巡礼记录。

该阶段围绕“当前点位”组织，不需要用户每次都回到完整计划列表查找目标。

### 2.8 巡礼记录

保存记录时会关联：

- 计划、作品和点位；
- 参考图和实景照片；
- 拍摄时间；
- 参考模式；
- 调色参数和结果图。

记录保存作品名和点位名快照。即使之后删除或重命名作品、点位，历史记录仍然
可以显示原始信息。

这是一个必须借鉴的数据设计。历史记录不能只依赖当前作品表的外键名称。

### 2.9 导出和分享

MiriaGo 支持：

- `.sjhplan` ZIP 数据包；
- Google My Maps CSV；
- 参考图/巡礼图对比图。

数据包包含 `manifest.json`，可选择：

- 只导入计划；
- 计划加记录；
- 是否包含完整参考图缓存；
- 导入前预览内容。

ENikki 应沿用这种可移植数据思路，但使用自己的格式和版本规则。

## 3. 技术实现概览

| 领域 | MiriaGo 做法 |
| --- | --- |
| 移动端 | Flutter |
| 桌面端 | Flutter Web + Tauri 启动器 |
| 状态管理 | `ChangeNotifier` + 应用级控制器 |
| 本地数据库 | SQLite + Drift |
| 文件资源 | 应用数据目录、本地缩略图和参考图 |
| 地图 | flutter_map + MapLibre，支持 OpenFreeMap、OSM、自定义 XYZ/style |
| 作品搜索 | Bangumi API |
| 巡礼点位 | Anitabi API/静态数据 |
| 账号与云同步 | 无 |
| 数据交换 | `.sjhplan` ZIP + `manifest.json` |
| CI | Android Release、Windows/macOS Desktop、iOS 无签名检查 |
| 测试 | 仓库中约有 45 个测试文件，覆盖数据、迁移、地图、相机和导入导出 |

### 3.1 本地优先

MiriaGo 没有后端服务。计划、设置、记录和资源均保存在本地：

- SQLite 保存结构化数据；
- 文件系统保存照片、缩略图和完整参考图；
- Repository 接口隔离 SQLite 与桌面端存储；
- 数据包用于迁移和备份。

这证明 ENikki 第一阶段不必先建设账号和云端，也可以做出完整产品。

### 3.2 地图适配

MiriaGo 把地图配置做成用户可选项：

- OpenFreeMap + MapLibre 样式；
- OpenStreetMap XYZ；
- 自定义 XYZ；
- 自定义 MapLibre style URL；
- 可配置 Anitabi 图片源及镜像回退。

这一点值得借鉴，但 ENikki 还要增加：

- 服务地址白名单和安全校验；
- 地图供应商许可审计；
- 离线 PMTiles 策略；
- 地图源失效后的自动回退和用户提示。

### 3.3 数据导入导出

MiriaGo 的 `.sjhplan` 设计包含清单、版本和可选资源，并在导入前预览。
ENikki 应采用同类设计：

```text
manifest.json
data/trip.json
data/records.jsonl
media/<sha256>.<ext>
checksums.sha256
```

关键不是文件扩展名，而是：

- 明确 schema 版本；
- 资源可选择性导入；
- 路径和校验和安全；
- 导入失败可回滚；
- 导出内容可长期恢复。

### 3.4 发布流程

MiriaGo 使用版本标签触发：

- Android APK 构建、签名检查和 GitHub Release；
- Windows/macOS 桌面安装包；
- iOS 无签名构建检查；
- Release Notes 自动生成。

它还没有覆盖 Linux 和 HarmonyOS，也没有自动完成 iOS TestFlight
签名和上传。这些是 ENikki 需要补足的部分。

## 4. 明确值得采用的设计

### 4.1 两级排序模型

ENikki 第一阶段采用：

```text
计划
├── 片区 A
│   ├── 点位 1
│   └── 点位 2
└── 片区 B
    ├── 点位 3
    └── 点位 4
```

比首版直接实现“时间窗 + 多交通方式 + 多日 VRP”更容易验证和交付。

### 4.2 点位状态

每个点位至少具备：

```text
pending   待巡礼
current   当前目标
completed 已完成
```

计划还保存当前片区和当前点位。这样现场页面可以直接回答“下一站去哪”。

### 4.3 点位允许暂无坐标

用户可以只填写作品和点位名称，之后再补坐标。无坐标点位：

- 不显示在地图；
- 不参与导航；
- 不参与距离计算；
- 不导出到地图 CSV；
- 补全坐标后自动恢复这些能力。

这能显著降低手动录入成本。

### 4.4 记录快照

记录必须保存：

- 作品名称快照；
- 点位名称快照；
- 来源 URL；
- 拍摄时间；
- 参考图快照或哈希；
- 实际照片本地路径。

不能只保存会变化的外键。

### 4.5 分级离线缓存

资源分成：

- 点位元数据；
- 缩略图；
- 完整参考图；
- 用户照片；
- 地图底图。

用户可以一键准备离线内容，界面显示缓存进度和失败项。

### 4.6 导入预览

导入数据包前先展示：

- 计划名称和数量；
- 作品、点位、记录数量；
- 包含的图片和文件大小；
- 冲突和重复项；
- 用户选择哪些内容导入。

比直接覆盖数据库安全得多。

### 4.7 文档和隐私

MiriaGo 提供：

- README 快速开始；
- 完整 `docs/USAGE.md`；
- 中英双语隐私政策；
- 示例计划和多张截图；
- 发布说明。

ENikki 应从一开始同步维护用户指南、隐私说明和截图，而不是等发布前补。

## 5. 不应照搬的设计

### 5.1 客户端硬编码 API 令牌

MiriaGo 源码中存在硬编码的 Bangumi 访问令牌。ENikki 绝不能这样做。

正确做法：

- 无需鉴权的请求由后端代理；
- 必须鉴权的请求使用服务端密钥；
- 客户端只使用短期、最小权限令牌；
- 任何测试 Token 都不得进入 Git 历史；
- 发布前执行 Secret 扫描。

### 5.2 依赖未公开的 Anitabi 静态数据

MiriaGo 会读取 Anitabi 的 `g.json`、`gN.json` 静态分页数据。这些地址
不是公开 API 文档中的稳定契约。

ENikki 不应复制这一实现。应使用：

- `/bangumi/{subjectID}/lite`；
- `/bangumi/{subjectID}/points/detail`；
- 图片域名按授权规则访问。

如果后续需要批量数据，应先取得 Anitabi 明确授权。

### 5.3 超大页面和仓储文件

MiriaGo 的 Anitabi 导入页面超过 3000 行，SQLite Repository 超过 2000 行。
这在高迭代期可以快速交付，但会增加维护、测试和多人协作成本。

ENikki 应按模块拆分：

- 地图控制器；
- 点位筛选器；
- 点位选择状态；
- Anitabi 导入用例；
- 单一点位卡片；
- 批量操作面板；
- 缓存任务队列。

### 5.4 桌面端结构

MiriaGo 使用 Flutter Web + Tauri 承载 Windows/macOS 桌面端。这个方案对
地图 WebView 和桌面文件能力有效，但并非六端方案。

ENikki 在 P0 仍需单独验证：

- Flutter 原生桌面；
- Flutter Web + Tauri；
- MapLibre 原生与 WebView；
- Linux 和 HarmonyOS 插件可用性。

在验证前不复制 MiriaGo 的桌面架构。

### 5.5 拍摄和自动调色优先级

这些是 MiriaGo 的差异化功能，但不是 ENikki 第一阶段闭环的必要条件。

ENikki 的顺序应是：

1. 行程、点位、片区和顺序；
2. 地图选点与离线参考图；
3. 当前目标、导航跳转和打卡；
4. 记录和导出；
5. 拍摄叠图、调色和分享效果。

否则容易把大量时间花在图像能力上，却没有可执行的巡礼计划。

## 6. 对 ENikki 的直接调整建议

| MiriaGo 经验 | ENikki 采用方式 |
| --- | --- |
| 计划、片区、点位三层 | 纳入 P1 数据模型 |
| 关键点和片区排序 | 纳入 P1，不等待复杂算法 |
| pending/current/completed | 纳入点位状态 |
| 地图内导入和选点 | 纳入 P1 验收标准 |
| 缩略图/完整图分离缓存 | 纳入离线准备流程 |
| 记录保存名称快照 | 纳入记录模型 |
| `.sjhplan` 数据包 | 改为 `.enikki`，保留选择性导入 |
| 可配置地图源 | 纳入设置，但增加许可和安全校验 |
| 本地优先、无账号 | 保持 P1 策略 |
| 自动化测试 | 每个核心模块必须配套测试 |
| 标签触发多平台发布 | 纳入 CI/CD，补 Linux、HarmonyOS 和 Apple 签名流程 |

## 7. 建议的 ENikki 首个闭环

```text
新建行程
→ Bangumi 搜索作品
→ 手动作品兜底
→ 在 ENikki 地图查看 Anitabi 点位
→ 单选/框选点位
→ 分配到片区
→ 设置片区关键点和顺序
→ 手动调整片区内部顺序
→ 缓存缩略图/完整参考图
→ 设置当前目标
→ 地图导航跳转
→ 打卡并保存记录
→ 导出 .enikki 数据包
```

这条闭环比“先做预算、订票跳转、账号和云同步”更能验证 ENikki 是否真正有用。

预算、交通、住宿和分享可以在闭环稳定后加入，但不能替代核心巡礼体验。

## 8. 总结

MiriaGo 给 ENikki 的最大启示是：

- 先把一个巡礼者从出发前到回家后的核心动作跑通；
- 用片区和手动排序降低路线规划复杂度；
- 本地化和数据可迁移应优先于账号和云端；
- 外部数据接入必须关注稳定性、授权和安全；
- 功能扩张要建立在测试、发布和用户文档之上。

ENikki 不需要复制 MiriaGo，但应吸收它的流程意识，同时修正其数据源、密钥管理
和代码组织问题。
