# 交通、住宿、用餐与预算规划

> 状态：核心产品方案  
> 日期：2026-09-14  
> 适用范围：P1 可执行行程闭环

## 1. 定位

交通、住宿、用餐和预算不是 ENikki 的附加功能，也不是核心巡礼体验完成后的
扩展项。它们与作品、点位和路线共同组成“可执行行程”。

ENikki 负责：

- 规划每一段交通，并记录时间、换乘、费用和来源；
- 规划每晚住哪里，以及住宿位置对每日路线的影响；
- 规划每天的早餐、午餐、晚餐、咖啡和临时用餐；
- 把所有费用纳入统一预算，并比较预估与实际支出；
- 生成交通、住宿、餐厅的第三方查询或预订入口；
- 在离线状态下保留已经确认的规划信息。

ENikki 不负责：

- 直接购买车票、机票、酒店或餐厅套餐；
- 处理支付、退款、改签、取消和售后；
- 保证实时库存、价格、班次、房态、排队时间或营业状态；
- 绕过第三方平台限制抓取订单、价格或库存数据。

## 2. 统一行程模型

所有规划对象都应进入同一条按时间排序的行程：

```text
行程
└── 第 1 天
    ├── 早餐
    ├── 从住宿到车站的交通段
    ├── 城际交通
    ├── 巡礼片区 A
    │   ├── 点位 1
    │   ├── 午餐
    │   └── 点位 2
    ├── 前往住宿的交通段
    └── 住宿
```

建议使用统一的 `PlanItem` 表达时间线，再通过 `type` 或子类型区分：

```text
spot        巡礼点
transport   交通段
lodging     入住或住宿安排
meal        餐次
rest        休息
free_time   自由活动
note        纯备注
```

算法可以调整时间线，但必须遵守用户锁定项、预约时间、营业时间、入住时间和
交通衔接。

## 3. 核心实体

| 实体 | 关键字段 | 说明 |
| --- | --- | --- |
| `TripTraveler` | 名称、类型、饮食偏好、过敏项 | 支持按人计算预算和用餐需求 |
| `TransportLeg` | 起点、终点、方式、时间、换乘、费用 | 一天内的实际移动段 |
| `TransportOption` | 班次、舱位/席别、价格、预订链接、来源 | 可比较的城际或长途交通方案 |
| `LodgingArea` | 区域、中心点、交通、便利度评分 | 住宿区域候选 |
| `LodgingOption` | 酒店、房型、日期、价格、早餐、退改 | 具体住宿候选 |
| `LodgingStay` | 入住日期、退房日期、已选酒店 | 行程采用的住宿安排 |
| `MealPlan` | 日期、餐次、时间窗、地点、用餐时长 | 行程中的一次用餐安排 |
| `MealOption` | 餐厅、坐标、营业时间、人均、预约链接 | 可比较的具体餐厅候选 |
| `DietaryPreference` | 素食、清真、过敏、忌口、儿童餐 | 纳入餐厅筛选和提醒 |
| `BudgetItem` | 类别、金额、币种、预估/实际、支付人、排序 | 行程预算与支出 |
| `BookingLink` | 平台、对象、深链接、来源、更新时间 | 只跳转，不保存账号和支付信息 |

金额继续使用最小货币单位整数加 ISO 4217 币种，禁止使用浮点数。

## 4. 交通规划

交通分为三层：

1. **城际交通**：飞机、火车、新干线、长途巴士、轮船、自驾。
2. **市内交通**：地铁、公交、电车、出租车、共享单车、步行、租车。
3. **点位衔接**：从当前点位到下一个点位、餐厅或住宿的最后一程。

每一段至少记录：

- 起点和终点；
- 出发与到达时间；
- 交通方式、线路、班次和换乘；
- 预计时长和距离；
- 费用、币种和人数；
- 预订状态与第三方链接；
- 数据来源和更新时间；
- 是否为固定预约、用户锁定或可调整项。

规划逻辑：

- 先安排有固定时间的城际交通和预约，再编排可移动的巡礼点。
- 计算步行、公共交通、驾车和骑行时间，识别赶不上车或过长的换乘。
- 允许设置“必须乘坐”“优先便宜”“优先少换乘”“避免夜间到达”。
- 交通时间不足时，提示移动点位、减少点位或调整日期。
- 导航跳转外部地图，实时班次以交通运营方为准。

第一阶段的交通规划可以是“手动选择加估算”，不要求一开始覆盖全球实时公交。

## 5. 住宿规划

住宿分两步：

1. 选择住宿区域；
2. 选择具体酒店或民宿。

### 5.1 住宿区域

区域评分建议综合考虑：

- 到主要巡礼片区的通勤时间；
- 末班车和首班车；
- 到机场、车站或长途交通节点的便利度；
- 餐厅和便利店的可达性；
- 每晚预算；
- 夜间到达和退房后的行李安排。

ENikki 应把住宿区域显示在每日路线和时间线上，帮助用户判断往返是否合理。

### 5.2 具体住宿

具体住宿信息包括：

- 入住和退房日期；
- 地址和坐标；
- 房型、人数和床型；
- 每晚价格、税费和服务费；
- 早餐、行李寄存和洗衣；
- 入住时间、退房时间和退改条件；
- 第三方预订链接；
- 用户确认的订单摘要。

订单号、入住人姓名和支付信息默认视为敏感数据，不进入公开分享内容。

### 5.3 与路线的关系

- 每天应有明确的出发住宿和返回住宿。
- 更换城市时自动生成退房与入住时间约束。
- 规划器不能把早晨或深夜点位安排到通勤不合理的位置。
- 住宿发生变化后，关联日期的交通和餐次应重新评估。

## 6. 用餐安排

### 6.1 餐次类型

支持：

- 早餐；
- 午餐；
- 晚餐；
- 咖啡、甜点和下午茶；
- 夜宵或临时用餐；
- 合作咖啡厅、主题餐厅和联动活动；
- 酒店早餐；
- 便利店、便当、超市和自带餐食；
- 用户自定义餐次。

### 6.2 每个餐次的信息

每次用餐至少包含：

- 日期、餐次和时间窗；
- 计划地点或候选区域；
- 关联的巡礼点、片区或住宿；
- 预计停留和排队时间；
- 预约时间与预约状态；
- 人均或总预算；
- 餐厅类型、特色和菜单摘要；
- 营业日和营业时间；
- 是否必须预约、是否支持单人；
- 饮食禁忌、过敏和儿童需求；
- 地图链接、官网或第三方预约链接；
- 数据来源和更新时间。

### 6.3 三种安排方式

#### 指定餐厅

用户已经选好某一家餐厅，时间线按预约或营业时间安排。

#### 按区域用餐

用户只指定“在宇治站附近吃午餐”，ENikki 在该区域和时间窗内提供候选，
不把行程绑死在具体餐厅上。

#### 弹性用餐

只保留一个时间窗，例如 12:00 至 13:30，现场再决定。适合便利店、
车站便当或巡礼节奏不稳定的路段。

### 6.4 与巡礼路线联动

- 午餐和晚餐应有合理时间窗，不能把用户连续安排到深夜。
- 如果餐厅有预约，预约时间应视为固定约束。
- 餐厅坐标应参与片区和路线计算，而不是只保存一段文字。
- 排队时间、营业日和前往餐厅的交通都应计入总时长。
- 餐厅临时关闭时，用户可以替换为附近候选，后续点位可自动重排。
- 联动咖啡厅可能需要提前抽选或预约，必须支持记录预约结果。
- 过敏和饮食禁忌应显著提醒，但最终仍需用户向商家确认。

### 6.5 数据和跳转边界

- 餐厅可以从用户手动录入、地图 POI 或合规的地点数据源加入。
- ENikki 不抓取点评网站，不伪造评分和排队时间。
- 座席预约、套餐购买或活动抽选只跳转第三方平台。
- 不保存第三方账号、银行卡或密码。
- 价格、营业时间和预约规则必须显示来源与更新时间。

## 7. 预算规划

### 7.1 预算分类

建议默认分类：

- 城际交通；
- 市内交通；
- 住宿；
- 餐饮；
- 门票与预约；
- 活动与联动消费；
- 购物；
- 保险与签证；
- 其他。

用户可以增加、隐藏和重命名分类，但核心分类用于汇总和导出。

### 7.2 金额模型

每笔预算同时支持：

- 预估金额和实际金额；
- 总金额和人均金额；
- 个人、同行者或共同支付；
- 原币种、基准币种和第二显示币种；
- 汇率、汇率来源和生效时间；
- 已支付、待支付和无需支付；
- 与具体交通、住宿、餐次或点位关联。

行程可以同时设置两个显示币种，例如 `CNY + JPY`。本地消费保留 `JPY` 原值，
在国内预订的费用可以保留 `CNY` 原值，两种币种在总预算、分类和每日汇总中
同时出现。换算值不能覆盖原始金额。

### 7.3 汇总视图

- 整趟行程总额，同时显示基准币种和第二币种；
- 按日期、城市、作品、片区和分类进行双币种汇总；
- 剩余预算与每日可支配金额；
- 预估与实际差额；
- 交通、住宿和餐饮三项的占用比例；
- 因人而异的费用分摊。

汇率数据不可用时保留最后一次成功值，但必须显著提示时间。预算计算必须覆盖
跨币种、舍入、负数、退款和多人分摊测试。

## 8. 预订和链接

交通、住宿和餐厅统一通过 `BookingProvider` 深链接：

```text
记录规划方案
→ 展示第三方入口
→ 用户跳转平台
→ 用户自行核对并完成交易
→ 用户回填已确认摘要
```

要求：

- 只允许白名单域名和外链协议。
- 明确标注平台名称和跳转目的。
- 如有推广或返利关系必须显式披露。
- 不通过 WebView 诱导用户输入第三方密码。
- 不把用户跳转行为与精确行程默认关联上传。
- 价格和可用性变化时，不把过期数据标记成已确认。

## 9. 离线与现场

出发前应缓存：

- 城际交通班次和预订摘要；
- 已选住宿地址、入住退房时间和订单摘要；
- 每日餐次、餐厅地址、预约时间和营业信息；
- 未预约区域的候选餐厅；
- 交通、住宿和餐饮预算；
- 相关地图位置和离线资料。

现场允许：

- 标记交通已乘坐、住宿已入住、用餐已完成；
- 记录实际时间和实际费用；
- 保存餐厅地址、菜单或预约截图；
- 临时替换未锁定餐厅或交通方案；
- 快速查看下一段交通、下一餐和当晚住宿。

## 10. 分阶段实施

### P0

- 建立交通、住宿、餐次、预算和同行者模型。
- 验证金额、日期、时区、币种和跨天住宿计算。
- 定义交通段、餐次和驻留时间的排线约束。
- 验证第三方深链接和敏感信息边界。

### P1

- 创建多日行程和同行者。
- 添加城际交通、市内交通和点位间移动。
- 选择住宿区域、录入住宿方案和入住退房时间。
- 安排每日早餐、午餐、晚餐和咖啡。
- 支持餐厅候选、预约状态、饮食禁忌和地图跳转。
- 建立交通、住宿、餐饮、门票和其他分类预算。
- 支持第三方预订和预约跳转，以及用户回填确认摘要。

### P2

- 接入合规的交通和地点数据源。
- 增加多方案比较、实时信息提示和汇率服务。
- 优化用餐与巡礼路线之间的时间约束。
- 支持多人预算分摊和协作调整。

## 11. P1 验收标准

用户可以创建一份三天、两人的巡礼行程，并完成：

1. 添加至少 20 个巡礼点。
2. 规划往返城际交通和每日市内交通。
3. 选择住宿区域并录入两家候选住宿，确认其中一家。
4. 为每天安排早餐、午餐和晚餐，其中至少两餐有预约时间。
5. 添加一位同行者的过敏或饮食禁忌，并在相关餐次显示提醒。
6. 为交通、住宿、餐饮、门票和购物建立预算。
7. 同时输入人民币和日元原始金额，正确显示 CNY + JPY 双币种汇总和两人分摊。
8. 通过第三方链接查看预订或预约页面，不完成站内交易。
9. 离线查看交通、住宿、餐次、预算和场地地址。
10. 导出后可在另一台设备恢复全部规划数据。

如果这十项没有完成，就不能把该版本称为“完整规划闭环”。
